# Technical Notes

## Employee category configuration

Employee branch, position, and employment status choices are stored in the `EmployeeCategory` table. The `type` values are `BRANCH`, `POSITION`, and `EMPLOYMENT_STATUS`; the migration seeds the existing employee-form options. Categories are soft-deactivated with `active = false`, preserving employee records that still contain an inactive value.

`/management/system-configuration` is available to administrators from the Settings & Configuration section in the sidebar. Account Settings appears in that same group for administrators and users with `/settings` access. The Workspace Reports shortcut is visible to administrators and users with `/attendance` access and links to the date-range report controls on Attendance. `/api/management/categories` allows administrators to list, add, and activate/deactivate categories. Authenticated users with employee-page access may read the categories for employee forms. New and updated employee profiles use active category values while preserving any currently selected legacy value.

## Benefits reports

The Reports sidebar item expands a submenu for SSS, Pag-IBIG, and PhilHealth. SSS links to `/reports/sss`; Pag-IBIG and PhilHealth remain coming soon while their layouts are being designed. Admin Page access includes a Reports permission keyed to `/reports/sss`; the sidebar, page proxy, and SSS APIs all enforce that permission for non-admin users. Completed SSS reports are persisted in `SssReport` and `SssReportEntry`; incomplete drafts are stored separately in `SssReportDraft` and are shared with users granted Reports access. Continuing a draft claims it and hides it from the shared list; closing without saving releases it, saving a draft releases it, and saving a completed report consumes it in the same transaction. Claims expire after one hour. SSS reports load ordered by employer name ascending, then applicable year descending and applicable month descending (newest period first within each employer), with creation time descending as a tie-breaker. The `/reports/sss` page content uses the available page width. The saved-report modal can use nearly the full viewport width. Its details area places unlabeled employer name, address, and SSS Number at the left in restrained typography; labeled PRN and Applicable Date appear together with a prominent Amount Due. Payment Details pairs Trans Ref# with Pay Date and Branch with Pay Type, with Amount Paid displayed at the same prominent size as Amount Due. Applicable Date is the applicable month's end date without “through” wording. Employer address and SSS number are snapshotted and shown in report detail, while the list view omits address. Amount Due is displayed with grouped thousands and two decimal places while its numeric value is submitted. The report form omits the month-end and employer employee-count helper lines. A contribution report requires an employee breakdown whose computed total matches Amount Due before it can be saved; a loan report requires a distinct saved loan account per row and permits manually adjusted due amounts independent of the saved principal balance. Payment details (amount paid, payment type, pay date, SSS branch, and transaction reference) are recorded separately after saving the report. Non-admin users with report access may enter initial payment details; the SSS payment PATCH route permits edits to existing payment details only for admins, using a conditional update to prevent concurrent non-admin edits. The UI disables edit controls for non-admin users once payment details exist. The API requires admin or Reports access, validates employer membership without filtering employee status, and recalculates contribution values server-side. `lib/sssContributionTable.ts` contains the 61-row schedule effective January 1, 2025, including regular SS, employer EC, and the SS/MPF split above ₱20,000 MSC. The official schedule review modal retains its complete contribution table with dark slate row text. Compensation range selection opens a compact searchable popup showing each range and its combined amount; after selection, the employee entry and report breakdowns display the chosen MSC value. The Employee Entries table uses a fixed layout sized to its popup, gives the employee name column extra width, and keeps its header and total summary visible while rows scroll vertically. MSC values use larger, high-contrast text in entry, preview, and saved report tables. Employee names use `Lastname, Firstname M.` format; the employee breakdown lists a sequential number, Name of Employee, SS Number, MSC, SS (employer and employee SS plus MPF), EC (employer EC), and Total Contribution. Contribution values use dark high-contrast text. Employee SSS numbers are snapshotted on report entries. Apply the SSS schema migrations with `npx prisma migrate deploy` before using the feature.

SSS contribution entry searches the full employee roster by SS Number, regardless of the selected report employer or employee status. Selecting a result fills the Employer employee selection and opens the compensation-range picker immediately; confirming a range adds that employee without changing or clearing existing entries. The report’s employer name, address, and SSS number always come from the employer explicitly selected in the form; each entry separately retains the employee’s actual employer details.

Standalone SSS loans are stored in `SssLoan`, separate from monthly SSS loan reports. `/api/reports/sss/loans` requires SSS Reports access, can list accounts across all employers or scope them to one employer, validates that the selected employee belongs to the selected employer on creation, and requires the employee's current Biometric Number on the server; the Add SSS Loan form and employee selector do not expose the number. The Loan Account Number is stored separately from the optional SSS transaction number. Approved Loan Amount records the approved principal, not net proceeds after service-fee or interest deductions. Approved principal may be unknown; when present, it remains the outstanding balance until actual employee loan payments are recorded in the future monitored loan-payments report. Unknown principal/balance is displayed as unknown. Scheduled amortization never reduces the outstanding balance and is not capped by that balance; users can adjust each report amount to match the SSS website's monthly due. Loan Date accepts a strict `YYYY-MM-DD` value with a four-digit year; invalid or overlong years are blocked from saving and do not reach the first-payment-month formatter. For salary loans, the first amortization is scheduled in the second calendar month after Loan Date. Loan statuses are `ACTIVE`, `PAID` (reason: applied for new loan or fully paid), and `NOT_CONNECTED` (reason: resigned). The loans dialog loads accounts across employers and defaults to Active, with Employer, Loan Account Number (LAN), and Active/Inactive filters plus search by employee name or SS Number. Its table shows only Employee, SS Number, Loan Account Number, Monthly Amortization, Status, and icon actions. View displays the saved loan details; Update edits its identifiers, dates, amounts, and status without changing its employer/employee; Delete is confirmation-gated and restricted to admins and super users in both UI and API. Deletion detaches report entries from the loan but retains their account-number and amount snapshots. Only Active accounts with a scheduled payment are offered for report generation. Loan reports create one row per saved loan account (multiple accounts for the same employee are supported), snapshot the loan ID/account number, display the account number read-only, and allow a positive manually entered due amount independent of estimated principal balance. Legacy employee-only loan draft rows can be removed and replaced with saved account rows before report generation. Employee names, codes, and biometric numbers are snapshotted, and deleting an employee detaches rather than deletes loan history. Loan mode's Loans button is always available regardless of the report Employer filter. Apply the `20261010140000_add_sss_loans`, `20261010150000_use_loan_date_for_amortization`, `20261010170000_support_sss_loan_status_and_account_entries`, and `20261010180000_allow_unknown_sss_loan_principal` migrations before using this feature.

SSS loan types are stored as `S` (Salary Loan), `C` (Calamity Loan), or `R` (Emergency Loan). The schema default and migration assign `S` to existing loans; the Add and Update forms require a valid type, and API writes reject all other codes. In the loans list, types use compact labels `S-Salary`, `C-Calamity`, and `R-Emergency`; Add/Update selectors and details use full names. The loan-list toolbar button is labeled View Loans, and the table includes Loan Date and Loan Type. Apply the `20261010190000_add_sss_loan_type` migration along with the preceding SSS loan migrations before using the type field.

Current Add SSS Loan behavior supersedes the older same-employer validation description above: the employee selector loads the full employee roster, including employees with no employer or an employer different from the selected loan Employer. The loan remains associated with the explicitly selected Employer for account management and reporting. The API still requires that both selected records exist and that the employee has a Biometric Number.

Employee employer snapshots remain available for searching SSS reports but are not displayed as subtitles below names in report employee rows.

## Employee directory views

Biometric Number is required in the new-employee form and is validated by the employee-create API; duplicate biometric numbers return a conflict. Employee edits keep the field optional so legacy records can still be updated. CSV employee imports also reject rows without a Biometric Number.

The employee card view shows a Delete icon beside View/Edit only to administrators and super-users. `DELETE /api/employees/[id]` independently authorizes those roles. Deletion is permanent: attendance records, punches, employee requirements, and requirement attachments cascade-delete; saved SSS report and loan records retain their snapshots and have their employee relation detached.

The icon-only Cards/List toggle, refresh-to-clear-filters, Transfer, Export, and Import controls are in the main toolbar, right-aligned and visible from the medium breakpoint; these controls are hidden on mobile. A left-aligned mobile magnifying-glass button toggles a vertically stacked search box and status, employer, and branch filters; its row keeps the Showing count beside it whether the filters are open or closed. A blue eye button immediately after the Branch filter opens the first alphabetically sorted employee in the current filtered result set, including active search/status/employer/branch filters; it is disabled when no employees match. On mobile it appears beside the Branch dropdown when filters are expanded. The collapsed mobile filter row and empty desktop quick-filter/count row do not reserve extra bottom spacing; the hidden transfer panel likewise has no collapsed bottom margin. Transfer appears before Export and Import. Activating it reveals employee selection checkboxes and an animated destination panel in normal document flow below the toolbar and filter row, so it cannot cover the employee cards. After at least one employee is selected, the destination branch and employer selectors and Transfer action are laid out horizontally when space allows and wrap on narrow screens; selectors use a consistent compact width instead of stretching to fill the panel. Branch and employer are independently optional; the `/api/employees/transfer` endpoint, available to admins and users with Employee Directory access, updates only supplied assignment fields. Successful transfers reload directory data and exit selection mode. The card shows bold Date Joined beside the photo; the list places the photo and name first, with the biometric number shown without a label below the name, followed by position, branch, employer, active status, phone, email, bold Date Joined, and actions. In list view, direct accessible View and Edit icon actions remain visible. The filter and quick-filter toolbars are in normal document flow and scroll away with the page. On desktop, the sidebar collapse button stays at the original `top-20` sidebar/header boundary, protrudes above the title header, and remains clear of the collapsed sidebar logo. Navigation summaries otherwise come from the authorized employee-detail response. The Back and previous/next links retain the filters, and the shared header action slot gives focus rings room to render. Employee CSV export opens the browser's native Save As picker when available. Browsers without File System Access support use the standard download flow and may use the browser's configured download location. Successful employee exports and imports display a dismissible success popup.

Employee `assignedBy` audit values remain stored as account IDs for historical compatibility. Employee detail and directory APIs resolve numeric IDs in a batch (directory) or single lookup (profile), returning the user's display name, username, or email in that priority order. Legacy emails remain unchanged, `ADMIN` displays as Admin, and missing account references display as an explicit unknown-account label rather than an unexplained numeric ID.

## Attendance toolbar

The attendance toolbar's Date Range controls end with the Go button, followed immediately by an icon-only Refresh button with an accessible label and tooltip (spinning arrow while running, disabled during refresh or report generation). Refresh re-fetches whichever report is active: when a date-range report is open it reloads that range's records, otherwise it reloads the daily report. The former "Clear report" text button was removed; report generation and the date-range selection remain the way to change or reset the view.

Requirements tab checklist lists now span the full inner width of each card, so labels and controls use the available space as the viewport resizes.

The Employee Profile Requirements tab shows three cards per row at the extra-large breakpoint and reduces the column count on narrower viewports. The selected profile tab is included in previous/next employee links and restored from the `tab` query parameter.

The Employee Profile Requirements grid uses one column by default, two columns from the medium breakpoint, and three columns at extra-large widths; the controls, errors, and completion count span the full grid width at each breakpoint.

The Employee Directory primary toolbar is one flex-wrapping group containing Back, Add, desktop Search employees, filters, the first-match eye action, view and refresh controls, Transfer, and admin-only Export/Import. Search grows into the remaining toolbar space from a 178px flex basis with a 140px minimum; status and employer dropdowns are fixed at 180px and Branch at 230px. Toolbar buttons and dropdowns do not shrink; they wrap as needed. Quick filters and the desktop Showing count remain in the separate row below. Dashboard employee stat links use `status=ALL|ACTIVE|INACTIVE`, `hiredWithin=30`, and `requirements=missing`; `clearSearch=1` clears any remembered directory search when entering from the dashboard. The employee list API provides completed requirement keys, the bypass flag, and BDO account IDs to support the missing-requirements filter.

The SSS Record Payment Amount Paid field uses a text input with decimal keyboard support: while editing it keeps a plain numeric string, and when blurred it displays locale-grouped thousands with exactly two decimals (for example "86,775.00"), preserving the numeric value for API submission.

SSS report drafts are visible to every authorized SSS Reports user. Continuing a draft atomically claims it so it disappears from the shared Saved Drafts list while being edited. Closing without saving releases the claim and restores it to the shared list; saving a draft releases the claim, and saving a completed report consumes the claimed draft transactionally. Claims expire after one hour to recover abandoned drafts. The saved Contribution Report view aligns Amount Due and Amount Paid in a shared summary row, removes the payment update action from the detail footer, and keeps Close sticky. The report table uses a wider Employer column, compact Period/Due headings (and Emp on narrow screens), and a tighter PRN-to-Employees gap. Row actions use eye, payment-edit, and admin-only report-edit icons. Admins can edit report employer, PRN, applicable period, amount due, and employee entries; the PUT API revalidates contribution/loan totals and rebuilds employee snapshots while preserving payment details. Non-admin report users may add initial payment details, while the PATCH API rejects attempts to change recorded payments. Generation groups Amount Due with Applicable Month and Year. Compensation range selection uses a narrower searchable dialog with a six-row visible scroll area and the target employee identified in the dialog header.

While an SSS report is being created or continued, meaningful form changes are automatically persisted to `SssReportDraft` after a short debounce. The draft remains claimed during autosave, and the claim owner can see and reopen their own claimed draft after a reload or server restart; other users cannot take over an active claim. Closing or explicitly saving a draft flushes pending edits before releasing the claim. Completed-report saving waits for in-flight draft persistence before consuming its draft.

The Generate Contribution Report dialog uses nearly the full viewport height. Its header and action footer remain visible while the form body scrolls, keeping Save Draft and Generate/Save Report available at smaller screen heights; the employee entry table keeps its own scroll area and totals summary.

Employee CSV export prevents repeated exports while a save is in progress. If the Save As picker stream fails after selection, it falls back to a regular browser download instead of attempting further writes or closes on that stream; canceling the picker still cancels the export.

SSS report review uses high-contrast text for PRN and applicable period values, and its employee count/amount summary sticks above the dialog actions while the review content scrolls. Employee-entry controls appear in the order Add Prev, Add All, and Add Entry. Add Prev loads the immediately preceding month’s saved report for the selected employer and report type, copies employees not already present, and leaves MSC/loan amounts blank. Add All and Add Entry refresh the selected employer's employee list before use; the API returns employees without filtering status, so active and inactive employer employees can be selected even when the report page has been open while employee data changed.

After a completed report save, an explicit draft save or release, or a payment save, the SSS Reports page refetches both saved reports and saved drafts from their APIs. This keeps the client-rendered lists current without a full document reload, and preserves the existing success notice.

The SSS Reports toolbar has a dedicated Drafts dropdown with the current saved-draft count; it is amber-highlighted while drafts are available, and users can continue or delete drafts from the menu. The report filters use an explicit All employers value so that option reliably clears employer filtering. Employer-specific filtering matches only the employer selected for the report, not the employers assigned to individual employees in its entries. A reset/refresh icon before the Year filter clears report search, employer, and year filters and reloads reports and drafts. The contribution schedule button is labeled SSS Table. Dashboard Quick Access includes a Reports shortcut only for users granted `/reports/sss` access; the visibility flag comes from the authenticated dashboard stats API.
