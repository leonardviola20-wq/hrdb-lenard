# Technical Notes

## Latest SSS report-list refinement

The shared saved Contribution and Loan report table labels the employee count `Emp` and uses `Status` and `Pay Date`; the transaction reference remains in its own column. It fills the available width without a forced 1280px minimum, using compact responsive padding and wrapping for long values on square and narrow screens. View remains a separate borderless eye button. Non-admin users receive a direct borderless Record Payment button while a report is unpaid; that same control is disabled once payment is saved, and no three-dot menu is shown. The horizontal three-dot menu is therefore reserved for admins, giving them Add/Edit Payment plus existing report edit/delete actions; it closes on selection, outside click, or Escape. The API independently rejects any non-admin attempt to edit a recorded payment.

In Reports > SSS Loans > View Loans, the Start Date column derives from each loan's API-serialized Loan Date and type. The API date parser accepts either a date-only value or Prisma's ISO timestamp serialization for display while preserving strict `YYYY-MM-DD` validation for form/API inputs. Salary and Calamity add two calendar months; Emergency adds seven, preserving the day where possible and clamping to month-end.

The View Loans modal has no Employer dropdown: its loan list and the **Report** action are scoped to the employer selected on the Reports dashboard. The read-only `Report` preview defaults to the `Active` filter and has `All`/`Active`/`Upcoming`/`Inactive` choices in its title header beside the Print action. `Active` shows ACTIVE loans linked to active employees whose calculated Start Date is in the current calendar month or earlier; `Upcoming` shows ACTIVE loans linked to active employees with a later Start Date; `Inactive` shows non-ACTIVE loan statuses; `All` combines those categories. Active employee statuses use the shared `isActiveEmployeeStatus` convention (`Regular`, `Contractual`, `Trainee`, and `Leave`). The preview shows Employee, SS Number, Loan Account, Loan Type, Loan Date, Start Date, Status, Monthly, and Semi-Monthly columns; Semi-Monthly is monthly amortization divided by two. Account count and combined monthly amortization update with the selected filter. Print prints only the filtered report with its current columns. It does not create or save an SSS report. Salary/Calamity Start Date is Loan Date plus two calendar months; Emergency Start Date is plus seven, preserving the day where possible and clamping to month-end. The loan-entry button is labeled **+ Add**.

## Employee category configuration

Employee branch, position, and employment status choices are stored in the `EmployeeCategory` table. The `type` values are `BRANCH`, `POSITION`, and `EMPLOYMENT_STATUS`; the migration seeds the existing employee-form options. Categories are soft-deactivated with `active = false`, preserving employee records that still contain an inactive value.

`/management/system-configuration` is available to administrators from the Settings & Configuration section in the sidebar. Account Settings appears in that same group for administrators and users with `/settings` access. The Workspace Reports shortcut is visible to administrators and users with `/attendance` access and links to the date-range report controls on Attendance. `/api/management/categories` allows administrators to list, add, rename, activate/deactivate, and permanently delete categories. Authenticated users with employee-page access may read the categories for employee forms. New and updated employee profiles use active category values while preserving any currently selected legacy value. Deleting a category removes only its selectable option; existing employee branch/position strings are not modified. The Employee Categories page shows six fixed-height rows in each independently scrollable list and uses the shared app-history-aware circular Back control beside its heading instead of the shell Back row.

Registered user management lets admins delete another account from `/admin` after an explicit confirmation. The API independently enforces admin access, rejects self-deletion and deletion of the final administrator, and performs the delete in a serializable transaction. Authored posts are deleted in that transaction; user-owned tasks and SSS drafts follow their existing cascade relations, while saved SSS reports remain with creator attribution set to null.

Standalone SSS loans are stored in `SssLoan`, separate from monthly SSS loan reports. `/api/reports/sss/loans` requires SSS Reports access, can list accounts across all employers or scope them to one employer, allows selecting any employee when adding an account, and requires the employee's current Biometric Number on the server; the Add SSS Loan form and employee selector do not expose the number. The Loan Account Number is stored separately from the optional SSS transaction number. Approved Loan Amount records the approved principal, not net proceeds after service-fee or interest deductions. Approved principal may be unknown; when present, it remains the outstanding balance until actual employee loan payments are recorded in the future monitored loan-payments report. Unknown principal/balance is displayed as unknown. Scheduled amortization never reduces the outstanding balance and is not capped by that balance; users can adjust each report amount to match the SSS website's monthly due. Loan Date accepts a strict `YYYY-MM-DD` value with a four-digit year; invalid or overlong years are blocked from saving and do not reach the first-payment-month formatter. The Loans dialog's Start Date column is derived from each saved Loan Date and loan type: Salary and Calamity loans use Loan Date plus two calendar months, and Emergency loans use Loan Date plus seven calendar months. The original day of month is preserved where possible and clamped to the target month's last day (including leap years); changing Loan Date or type and saving automatically refreshes the derived date. This display date is distinct from the first amortization month used to determine payment-report eligibility, which remains the first day of the offset month. Loan statuses are `ACTIVE`, `ON_HOLD` (employee-initiated hold, no reason), `PAID` (reason: applied for new loan or fully paid), and `NOT_CONNECTED` (reason: resigned). On-hold loans appear under the Inactive filter and are excluded from report entry. It prefills the scheduled payment when positive, otherwise the monthly amortization. Report create/edit APIs accept these cross-employer and not-yet-due account entries but continue requiring a unique saved Active account linked to the selected employee. Loan reports create one row per saved loan account (multiple accounts for the same employee are supported), snapshot the loan ID/account number, display the account number read-only, and allow a positive manually entered due amount independent of estimated principal balance. Legacy employee-only loan draft rows can be removed and replaced with saved account rows before report generation. Employee names, codes, and biometric numbers are snapshotted, and deleting an employee detaches rather than deletes loan history. Loan mode's Loans button is always available regardless of the report Employer filter. Apply the `20261010140000_add_sss_loans`, `20261010150000_use_loan_date_for_amortization`, `20261010170000_support_sss_loan_status_and_account_entries`, and `20261010180000_allow_unknown_sss_loan_principal` migrations before using this feature.

SSS loan types are stored as `S` (Salary Loan), `C` (Calamity Loan), or `R` (Emergency Loan). The schema default and migration assign `S` to existing loans; the Add and Update forms require a valid type, and API writes reject all other codes. In the loans list, types use compact labels `S-Salary`, `C-Calamity`, and `R-Emergency`; Add/Update selectors and details use full names. The loan-list toolbar button is labeled View Loans, and the table includes Loan Date and Loan Type. SSS loan statuses include `ON_HOLD` for an employee who has chosen to pause the loan, with no reason required. On-hold loans appear in the existing Inactive filter and are excluded from generated loan reports because reports only include `ACTIVE` loans.

Current Add SSS Loan behavior supersedes the older same-employer validation description above: the employee selector loads the full employee roster, including employees with no employer or an employer different from the selected loan Employer. The loan remains associated with the explicitly selected Employer for account management and reporting. The API still requires that both selected records exist and that the employee has a Biometric Number.

Employee employer snapshots remain available for searching SSS reports but are not displayed as subtitles below names in report employee rows.

SSS loan entry table rows must not contain literal whitespace text between adjacent `<td>` elements, because it creates invalid children under `<tr>` and triggers a hydration error. Loan identifiers and amounts in both report preview and saved-report tables use explicit dark slate text for readable contrast.

## Card entrance animation

Employee directory cards and Tasks column cards fade in with a subtle upward lift so they appear one-by-one instead of popping in all at once. Each card gets the `card-lift` class plus an inline `animationDelay` of 60ms times its index within the list/column, capped at the first twelve cards (~720ms) so long lists do not crawl; this keeps an even cadence with no skipped step. The effect is defined by a `@keyframes card-lift` rule and `.card-lift` utility in `app/globals.css` and is disabled under `prefers-reduced-motion: reduce`. It applies to the Employees cards view (not the table/list view) and to every Tasks column; no data, state, or API behavior is affected.

## In-app navigation history and Back controls

`lib/appNavigationHistory.ts` keeps a trail of the HRDB routes the browser has walked through in this session (full keys of `pathname + search + hash`), with a cursor that mirrors the browser's position. Entries are recorded through three change kinds: `push` (truncates any forward entries and appends), `replace` (overwrites the current entry so no extra Back step is created), and `traversal` (moves the cursor to the matching earlier/later entry, restarting the trail when the arrival route was never recorded). `canGoBackWithinApp()` is true only when the cursor sits past the first recorded entry, which means an in-app Back action can call `router.back()` without ever leaving HRDB for an external page.

`components/AppNavigationHistoryTracker.tsx` is a null-rendering client component mounted by `AppShell` (on both the signed-in and public branches) that patches `history.pushState` / `history.replaceState` and listens for `popstate`, so every Next.js client navigation, in-page link, and Back/Forward traversal is recorded with the right kind. The landing page, `/login`, and `/register` are never recorded, so a Back control cannot return an authenticated user to a signed-out screen, and `Sidebar`'s logout clears the trail before navigating to `/login`. A hard page load records the current screen as the first entry, which is why a directly opened or bookmarked page has nothing to go back to and uses its fallback.

`components/HistoryBackLink.tsx` is the reusable route-level Back control: it renders a normal `Link` whose `href` is the safe destination and, when `canGoBackWithinApp()` is true at click time, calls `router.back()` instead. Modified clicks (meta/ctrl/shift/alt), non-primary buttons, and handled clicks are left to the browser, so open-in-new-tab still uses the fallback URL. This keeps browser-managed scroll restoration and forward history intact while still giving direct visitors a deterministic destination. It backs the AppShell Back row (`components/Sidebar.tsx`), the Employee Profile tab-row control (falling back to the directory URL built from the preserved filters), and the Employee SSS Contributions page (falling back to `/employees/[id]?tab=Government`). The Employee Directory, Tasks, and Attendance toolbars no longer render a Back control, and the AppShell Back row is hidden on the Dashboard, Reports, Tasks, Employees, Contacts, and Employers pages.

Behavior notes that supersede the earlier lines above: the Employee Profile Back control and the SSS Contributions Back control are now history-aware rather than fixed links; the SSS Contributions page no longer relies on the AppShell `backHref` (it still hides the app-shell Back row and renders its own circular chevron-only button, whose fallback destination targets the profile's Government tab); and the Employee Profile's selected tab is written to the `tab` query parameter on every tab change as a history *replacement* (existing query values such as the directory filters are preserved, and the legacy `tab=Government ID` alias still resolves), so browser Back/Forward reopen the tab that was on screen and returning from a deeper page — including SSS Contributions — restores it.
