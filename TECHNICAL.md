Development may derive the target database names from `DATABASE_URL`. ## Direct Messaging

The signed-in app shell mounts a floating chat widget on every authenticated page. Its launcher opens an online-user list (three initially, with View all) or the selected direct conversation. The old Chat page and sidebar entry are removed; `/chat` redirects to the Dashboard for bookmarked links. A launcher unread badge and in-app message toast report incoming messages while the user is in the app. No browser/OS notification permission is requested. The widget polls presence every 15 seconds, conversations and the inbox every two seconds, and sends messages through the authenticated chat API.

Chat UI components are grouped under `components/chat/`. `DirectMessageWidget` composes the floating widget, `useDirectMessageWidget` owns its polling/state/API orchestration, and focused components render the conversation, message list, composer, online roster, toast, and launcher. API routes and the shared chat store remain unchanged.

The direct-message composer sends lightweight typing activity to the selected recipient and shows their “is typing” status. Typing updates refresh every 2.5 seconds while the composer is active and expire after five seconds in memory; the client clears the status on idle, send, conversation close, or widget minimize. The composer and per-message reaction controls use a searchable, category-based emoji picker. Selecting an emoji in the composer inserts it at the current text selection, and typing/pasting emoji remains supported. Each message supports up to 20 distinct emoji reactions; either conversation participant can add or toggle off their own reaction, and the widget displays aggregate counts and the current user's selected state. Reaction updates use an authenticated, rate-limited endpoint and remain in the in-memory thread. The emoji and send buttons align to the bottom of the message field, including when it expands to multiple lines.

The app shell sends an authenticated presence heartbeat every 15 seconds and removes its session when it unmounts. User-initiated logout awaits presence cleanup before clearing the auth cookie, and cleanup is idempotent across logout and component unmount. An unauthorized best-effort cleanup after an already-expired session is not logged as an application error. Sessions expire after 60 seconds without a heartbeat, covering abrupt browser closures. The authenticated `/api/chat/presence`, `/api/chat/messages`, `/api/chat/messages/inbox`, and `/api/chat/typing` routes are available to every signed-in user; Chat access is not controlled by admin-managed page permissions. Inbox polling uses a monotonic in-memory message sequence cursor, initializes without replaying older messages, and paginates batches of up to 50. The global chat store is versioned across development hot reloads: compatible in-memory state is retained, while a legacy/incompatible store is reset so old messages cannot break inbox polling or strict message validation. Presence, typing activity, and message threads are held only in the local Node process memory; messages are not stored in the database, and inactive threads expire after one hour. Threads retain at most 100 messages. This design requires a single shared Node process; restarting it clears online status and all chat history.

Every authenticated user can open the floating widget, appears online while signed in, and can send or receive direct messages. `/admin` no longer offers Chat as a per-user page permission; any legacy `/chat` permission values are ignored.

## In-app navigation history and Back controls

`lib/appNavigationHistory.ts` keeps a trail of the HRDB routes the browser has walked through in this session (full keys of `pathname + search + hash`), with a cursor that mirrors the browser's position. Entries are recorded through three change kinds: `push` (truncates any forward entries and appends), `replace` (overwrites the current entry so no extra Back step is created), and `traversal` (moves the cursor to the matching earlier/later entry, restarting the trail when the arrival route was never recorded). `canGoBackWithinApp()` is true only when the cursor sits past the first recorded entry, which means an in-app Back action can call `router.back()` without ever leaving HRDB for an external page.

`components/AppNavigationHistoryTracker.tsx` is a null-rendering client component mounted by `AppShell` (on both the signed-in and public branches) that patches `history.pushState` / `history.replaceState` and listens for `popstate`, so every Next.js client navigation, in-page link, and Back/Forward traversal is recorded with the right kind. The landing page, `/login`, and `/register` are never recorded, so a Back control cannot return an authenticated user to a signed-out screen, and `Sidebar`'s logout clears the trail before navigating to `/login`. A hard page load records the current screen as the first entry, which is why a directly opened or bookmarked page has nothing to go back to and uses its fallback.

`components/HistoryBackLink.tsx` is the reusable route-level Back control: it renders a normal `Link` whose `href` is the safe destination and, when `canGoBackWithinApp()` is true at click time, calls `router.back()` instead. Modified clicks (meta/ctrl/shift/alt), non-primary buttons, and handled clicks are left to the browser, so open-in-new-tab still uses the fallback URL. This keeps browser-managed scroll restoration and forward history intact while still giving direct visitors a deterministic destination. It backs the AppShell Back row (`components/Sidebar.tsx`), the Employee Profile heading (falling back to the directory URL built from the preserved filters), and the Employee SSS Contributions heading (falling back to `/employees/[id]?tab=Government`). The Employee Directory, Tasks, and Attendance toolbars no longer render a Back control, and the AppShell Back row is hidden on the Dashboard, Reports, Tasks, Employees, Contacts, and Employers pages.

Behavior notes that supersede the earlier lines above: the Employee Profile and SSS Contributions Back controls are history-aware rather than fixed links and sit beside their page headings; the SSS Contributions page does not rely on the AppShell `backHref` (it still hides the app-shell Back row, with its own heading Back control falling back to the profile's Government tab); and the Employee Profile's selected tab is written to the `tab` query parameter on every tab change as a history *replacement* (existing query values such as the directory filters are preserved, and the legacy `tab=Government ID` alias still resolves), so browser Back/Forward reopen the tab that was on screen and returning from a deeper page — including SSS Contributions — restores it.

### PhilHealth reports
The Reports dashboard PhilHealth actions require the selected employer and open `/reports/philhealth?view=employees` or `?view=payments`, preserving `employerId`. Its Employee List loads employees assigned to the selected employer plus accounts previously linked to it; Add Account deliberately offers the full employee roster, listing employees assigned to the selected employer first, and associates the employee with that employer without changing `employee.philHealth`. Account status is employer-specific and active by default. Search, All/Active/Inactive, reset, eight-row pagination, and list-wide active/inactive totals are supported.

Monthly `PhilHealthReport` rows are unique per employer and applicable month/year; employee amounts are entered manually and stored as `PhilHealthReportEntry` snapshots. The server validates active employer-scoped accounts and sums integer cents to calculate Amount Due. `PhilHealthPayment` is stored separately with Payor Name, PEN (the employer `phic` snapshot), SPA, Applicable Period, Amount Paid, Accredited Collecting Agent, Transaction Confirmation No., Transaction Date, ePAR No., and ePAR Date. The Payments page lists saved payment details; the dashboard previews the eight latest payments by transaction date. APIs use Reports authorization and scope all records to the selected employer.

The Prisma migration is `prisma/migrations/20261021120000_add_philhealth_reports`; it was applied with `npx prisma migrate deploy` after explicit authorization. Follow-up `npx prisma migrate status` reports the database schema up to date, and account routes can use the new tables. The PhilHealth Reports and Payments tables expose a borderless eye "View report" action for every user with Reports access. It opens a report-details modal that renders the employer name and PHIC number, the applicable period, Amount Due, Amount Paid, a Paid/Partial/Unpaid status badge, every saved `PhilHealthReportEntry` (employee name, employee code, PhilHealth number, contribution) with an entry-count and total footer, and the full `PhilHealthPayment` metadata grid.
